# CLAUDE.md

turri desktop (this repo, `turri-oss/turri-desktop`) is a proof of concept: [turri](https://github.com/turri-oss/turri) as a native Electron app for people who do not live in a terminal. It runs turri's own conversation and work loop and shows them in native UI - never turri in a terminal in a window. The one terminal there is, the preview's, is for trying the app turri builds. `docs/window.md` says what the window offers, the README its short tour.

## Shape

```
electron/main.ts     the windows, each a workspace (its project, engine, preview, terminal), native menus, dock, appearance and zoom - and the bridge to each engine
electron/turri-version.ts  which turri runs - npm's pinned version, or a clone at a commit - and whether it is behind
electron/updates.ts  the app's own updates, from its GitHub releases: checked, downloaded, installed on a restart
electron/settings.ts the app's settings beyond its look - new projects' models, updates - in settings.json
electron/shell-env.ts the person's login shell's environment - PATH, API keys - read as the app starts when it was not started from a terminal; every engine waits for it
electron/preview.ts  the preview: a WebContentsView over the Preview view's space, and the browser tools' actions in it
electron/terminal.ts the preview's terminal: a shell on a pty, a headless xterm of its screen, and the terminal tools' actions
electron/terminal-input.ts  the keys and the mouse as an xterm sends them, the modes a program turns on for them, and the cell a text is in
electron/preload.ts  window.turri: the engine's methods, a few native services, the events the window is sent - all a sandboxed window has
engine/engine.mjs    one process per open project: the methods the window calls, and the events it emits
engine/chat.mjs      turri's session (createTurri) and its chats, each pi's agent session; their UI calls become window events, each with its chat
engine/entries.mjs   what a chat says - pi's messages, turri's entries (a pulse's end, the sentinel's notices, which the status panel shows) - as the window's items
engine/auth.mjs      signing in to the model providers: pi's logins, their prompts and events as window events
engine/browser.mjs   browser tools on the preview: a pi extension of the app's, loaded beside turri's
engine/terminal.mjs  terminal tools on the preview's terminal: another
engine/app.mjs       where turri is: the window as turri's host surface, and what the person has open, each turn
src/                 the window: React, no UI kit, one stylesheet (styles.css)
tests/               the window's tests: Playwright's Electron support on a fixture project, calling no model
```

- **turri comes from npm**, as `@turri-dev/cli/host` - turri's public entry for hosts (`docs/hosting.md` in turri). The engine imports only that, through `engine/turri.mjs`; anything else it needs is added to turri's `src/host.ts` first, never reached for by a deep path. For working on both at once, `TURRI_DEV=<clone>` loads the clone's `src/host.ts` instead - `npm run dev` sets it to `../turri` when that is there, `npm run dev:npm` keeps the package - Node runs its TypeScript as it is, so no build - and a change to turri is in at the next project opened. The version is pinned exactly, because a 0.x prerelease may change the entry: a push to turri's `main` publishes `@turri-dev/cli@<x>-next.<sha>`, and `npm install @turri-dev/cli@next` takes it. To try a turri not yet published: `npm pack` in the turri clone, then `npm install <the .tgz>` here - and never commit a `package.json` that names a tarball.
- **What turri knows is turri's: never written again here.** The ***plain grammar and parser, what a module imports and requires and which file each is, its definitions and concepts, the standard library, its kinds and conformance templates - the app takes all of it from the host entry. No regex or walker of the app's reads a `.plain`'s front matter, sections or concepts, and no copy of a turri function, pattern or table stands in for one the entry does not export. When it lacks one, do not work around it: explore turri for what is there, and write a prompt for a Claude session in the turri clone that adds it to `src/host.ts` (and `docs/hosting.md`, with tests) - reusing turri's own code, not adding a second copy - and give it to the person to run. The app then uses it, through `TURRI_DEV` until a turri that has it is published and pinned; on a turri without it the feature is left out (`turri.x === undefined`), as with `debugMode`.
- **A new turri is a new app.** turri stays pinned; the app updates itself (`electron/updates.ts`, electron-updater) from its GitHub releases, which a tag `v<version>` builds into a draft (`.github/workflows/release.yml`) - out once published by hand. On macOS only a build signed with a Developer ID updates: an ad hoc one says it cannot.
- **The engine runs on Electron's own Node**, forked with `ELECTRON_RUN_AS_NODE=1`: the package is compiled JavaScript, so no system Node is involved. Its `console` is turri's terminal output, redirected to `log` events.
- **One window per project.** Each window is a workspace in `electron/main.ts` - its own engine, preview and terminal - and the IPC handlers find theirs by the window that asks (`workspaceOf`); the menu acts on the window in front (`focused`). A project opens in the window in front if it has none, a new window otherwise, and one already open is brought forward (`openWhere`): never two engines on one project.
- **One work loop per project, several chats on it.** turri's session (`createTurri`) owns the job registry and work loop and holds up to nine chats, each its own pi session; the engine reads `jobs` and `loop` from it and is told of each job (`onJobChange`). The window shows the chats as folder tabs in the chat's header (`src/chats.ts` keeps each one's state, from events carrying `{ chat, data }`): ⌘T opens one (`openChat`), ⌘W closes the one shown (`closeChat`) - the window, with one left - ctrl+tab and ctrl+shift+tab go along them, ctrl+c, wherever the focus is while the chat is open (not in the preview's terminal), is the terminal's: at a question, turri's `decline` (or pi's dialog dismissed), each one, the turn going on; else turri's `interrupt` (a chat's work stopped, or, in one doing nothing, its draft cleared, else the session ended and the window closed by the main process on the engine's `ended`). A question over unanswered - its dialog's `signal` - is put away (`chat:unask`) - and showing one tells turri (`focusChat`), which reports a closed chat's pulses there. Escape, as in pi's terminal, only stops a chat at work - never clears a draft or ends turri - and only once nothing else is open for it to put away. The window's buttons say what the person would type, in the chat shown - Regenerate is `/regenerate <file>` - so a button never starts a second loop. On a turri without `createTurri` (0.1.16 and before), one chat, made from `createTurriExtension`, and no tabs. Halting a pulse is turri's alone: the window offers no Halt or Stop for one. The engine's own loops are `dryRun` (Preview plan, drift) and start nothing.
- **turri's questions are docked in the chat**, in the message box's place - never a sheet over the window. `ask_user` reaches the window through `dialogs(chat)`, with the chat it is of - a hidden chat's waits in it, its tab marked; the extension's other dialogs (select, confirm, input, editor) through the `uiContext` in `chat.mjs`. A terminal component it draws (`ui.custom`: a panel, a picker) has no window form and resolves at once - except the `turri-skill` widget, a running skill's phases: `chat.mjs` draws it plain and reads its lines back into `chat:progress`, which the chat shows above its message box.
- **turri is told it is in the app.** turri's prompt speaks of its terminal - the side panel on ctrl+h, /pulses - unless its host gives a surface (`TurriHost.surface`, turri's docs/hosting.md): then it leaves the terminal out and puts the host's words in its place. `APP_SURFACE` in `engine/app.mjs` is the window in those words; `TurriHost.systemPrompt` adds, each turn, which view and file the person has open (the window says it with `look`). When the window changes - a view, a button, a mark - say it in `APP_SURFACE` too. The sentinel has a prompt of its own, without `APP_SURFACE`: `SENTINEL_SURFACE` (turri's `sentinel.surface`) tells it of the preview, where the person watches it try a release with the tools it is given - change it with the preview or those tools. A turri without `surface` (0.1.7 and before) ignores both.
- **Signing in is the window's**, never pi's terminal dialogs: `engine/auth.mjs` runs pi's `ModelRuntime.login` - through the open chat's `session.modelRuntime`, so the conversation has the credential at once, or a runtime of the engine's own before a project is open - and sends its prompts and events to the sign-in sheet (`src/AuthSheet.tsx`), answered by id. The main process opens an `auth_url` in the browser; the OAuth callback server stays in the engine, and the page it sends - pi's, with no way given to change it - goes out as turri's (`turriCallbackPage`), told by its markup. `/login` typed in the chat opens the sheet instead of reaching the model. Test against a scratch `PI_CODING_AGENT_DIR`, never the person's `~/.pi/agent/auth.json`.
- **The preview is a page of its own**, in a browser session of its own - in memory, new for each project opened - a `WebContentsView` the main process lays over the rectangle `PreviewView` reports - in the window's pixels, its CSS ones times the zoom. Nothing of the window draws over it: while a sheet is open it is taken away (`covered`), and so are its empty and failed states, which the window draws in its place. turri's browser tools (`engine/browser.mjs`) are the app's, not turri's: each is a request from the engine to the main process (`{ browser, id, params }`, answered `{ reply }`), done in that same pane, which the window shows while they run. They go to localhost only. Clicks and typing run in the page as the person's gesture, so the pages they open are in its history; a click by text or at a point (`browser_click`) is real input (`sendInputEvent`), at a point in the page's CSS pixels, which a screenshot is kept in, and so are keys pressed (`browser_press`) - each down, held, up, alone or together - for what listens to the keyboard itself, a game; what runs in the page is a function sent as its source, and says what went wrong rather than throwing. Only the newest screenshot is sent to the model as an image, and none once a model has refused one (the `context` event): the refused turn is marked for pi to retry, and goes on without it.
- **The preview's terminal is the other way to try it**, beside the browser - a switch in the Preview bar (`Pane`), each project's choice remembered. The main process runs a login shell in the project's folder on a pty (node-pty, its macOS prebuild: `scripts/pty.mjs` makes its `spawn-helper` executable after each install) and keeps its screen in a headless xterm; the window draws it with xterm.js from `terminal:data`, replaying what it has said when drawn again. turri's terminal tools (`engine/terminal.mjs`: run, type, press, click, scroll, screenshot, read) are requests like the browser's (`{ terminal, id, params }`) and bring the window to the terminal; a command is done once the shell is back at its prompt (the pty's foreground process), or once it has gone quiet with a program still running - waiting for input, or serving. Keys and the mouse are sent as an xterm sends them (`electron/terminal-input.ts`): a key with its modifiers by one grammar (ctrl+q, shift+tab, f5) for press and type, and a click or the wheel only to a program that has turned on mouse reporting, in the encoding it asked for - both modes, and application cursor keys, heard from its output and forgotten when it ends; the window marks the cell (`terminal:pointer`). A screenshot of it is the window's own pixels over xterm's screen (`captureTerminal`), sent to the model as the browser's are, only the newest of either an image. Which of the two turri tries something in is its own choice, by what it is - `APP_SURFACE` says how, and to open there what is released - after a pulse (`release-after-pulse`) or when asked - and say what to test.

- **The window is sandboxed.** `sandbox: true`: the preload requires only `electron`, and every `window.turri` call is a message the main process checks - a path in the window's project (`inProject`), a setting there is (`pickSettings`), a sign-in method. A new method says what it accepts. The window never navigates, and opens only web links, in the browser. `docs/privacy.md` and About's privacy tab say what is sent where: change both when that changes. The third-party notices are built (`scripts/notices.mjs`); a package bundled into the window goes in its `IN_THE_WINDOW`.

- **macOS and Linux.** What differs is said in one place on each side: `MAC` in `electron/main.ts` (the window draws under the traffic lights on macOS and keeps the window manager's title bar on Linux; the app menu, Open Recent, the Dock and Finder are macOS's) and `src/platform.ts` in the window (`keys("S")` is ⌘S or Ctrl+S, `withMod(event)` the key a shortcut is pressed with, `REVEAL` the file manager's name), with `data-platform` on `:root` for the stylesheet. Never write ⌘ or Finder into the window as it is. On Linux, Ctrl+C in the preview's terminal is the shell's: it copies on Ctrl+Shift+C.

## The window

- **The ***plain editor is two layers**: a transparent textarea over a `<pre>` coloured by turri's own grammar (`highlightSpec`). They sit in one scrolling box and share every font and padding rule, so they wrap alike - a difference in width or font between them puts the caret on the wrong line. After touching either, `npm test` measures both (`tests/spec-editor.spec.ts`).
- **Colours are turri's**: turri-dark (the default) and turri-light, from turri's `.pi/themes/` and its ***plain palette, as tokens on `:root[data-theme]` in `styles.css`. Use the tokens; `system` follows macOS. `--built` (turri's pink) and `--tested` (its neon cyan) are what is regenerated and what is conformance tested, wherever either shows: a functional spec's mark, a pulse's kind. The choice and the zoom level live in `appearance.json` in the app's userData.
- **Fonts**: San Francisco, the system's own, everywhere - nothing bundled. Its sans (`--sans`, the `--body` token) for the interface and the ***plain - the editor, a pulse's ***plain, a ```plain block in the chat; the system's monospace (`--mono`: Menlo, as Chromium cannot reach SF Mono, or SF Mono where installed) for what has to be monospaced: code, diffs, transcripts, the preview's terminal and `kbd`. On Linux, the system's sans and monospace. The interface has the shapes of turri's design system (its Figma, as turri.dev has them): square (`--radius` and `--radius-small` are 0), spacing on a 4px grid (2 only for pixel gaps), and shadows hard, with no blur - a 2px line under what stands up (`--shadow`), a 3px notched pixel border for what matters (`--pixel-border`: a pulse's card; `--pixel-border-active`, neon, the one marked or chosen), a pixel box on a 12px hard base for what floats (`--float`: a sheet, a menu, a notice). The primary button is pink with a pixel bevel (`--action`, `--bevel`), lifting 2px on hover in a step; focus is a 2px neon ring 4px out. Pixel things snap in `steps()`; glows - only neon or grauzone at a low alpha - ease.
- **The ***plain mark** is ***plain's logo, its three asterisks, in its green #79FC96: `public/plain/plain-mark.svg`, cropped to the marks, drawn by `PlainMark` in `ui.tsx` beside a `.plain` file's name - the file tree (its state dot at the right, with how much of it is built), the ***plain view's header, a pulse's ***plain.
- **The jellyfish** is turri's pixel kit, from the D5-Lean design: `src/pixels/turri-pixels.js` and `.css` (its animations, in `tp-` classes), and its static SVGs in `public/jellyfish/`. `Jellyfish` in `ui.tsx` draws it: large, `jellyfish-hero.svg` at rest, the kit's swaying hero (`mountSprite`) swimming, and its lifecycle (`mountJellyfish`: the polyp grows into the jellyfish, sinks, grows again) - each mounted in the kit's own pixel box and scaled. Below 48px, `logo-mark.svg`, still at rest and swimming jumping a pixel at a time (`bob`, in steps). Only the chat's move - the empty chat's lifecycle, and the turri icon on the line saying what turri is doing; every other jellyfish - the welcome screen's, the chat's header, the preview's - stays still (`swimming={false}`). The app icon is drawn from `logo-mark.svg` too (`npm run icon`). Working is the design system's building loader (`Spinner` in `ui.tsx`, its `loader/building`): the mark filling in a pixel every 60ms in reading order over its outline, held half a second, then over - every loader on one clock, still and whole with reduced motion.

## Checking a change

`npm run typecheck` and `npm test` - Playwright's Electron support driving the real window on a copy of `tests/fixture/hello`, its userData and pi's folder in a scratch folder, calling no model (`tests/app.ts`; docs/development.md says more). Add a test there for what you change when it calls no model. Then look at the real window - for what a test does not reach. `electron/main.ts` has development hooks for that:

```bash
TURRI_APP_OPEN=<project dir>          # open a project at start
TURRI_APP_VIEW=spec|work|stdlib       # switch to a view
TURRI_APP_SCREENSHOT=<file.png>       # capture the window after ~2.5s and quit
TURRI_APP_HIDDEN=1                    # draw the windows but never show them, and keep out of the Dock - the tests do
npm run build && TURRI_APP_OPEN=../turri-projects/guestbook TURRI_APP_SCREENSHOT=/tmp/shot.png npx electron .
```

The hooks are heard only from source: a packaged app (`npm run dist`, `electron-builder.yml`, `docs/development.md`) ignores them, and TURRI_DEV. For anything a screenshot cannot show - layer sizes, fonts loaded, a menu action - load `dist-electron/main.cjs` from a small script run with `npx electron <script>` and `executeJavaScript` in the window. Such a script runs as the app "Electron": what it saves goes to `~/Library/Application Support/Electron/`, not the app's own userData; clean up there afterwards.

Regenerate, Preview plan and every chat message call the project's models and spend money; Regenerate also changes the project. Check with what calls no model - opening a project, the ***plain, slash commands that only print (`/stdlib`) - unless the person asks for a real run.

## Conventions

- The name is **turri**, lowercase, even at the start of a sentence; ***plain is written `***plain`. The window draws it as its name: ***plain's mark, then plain - `<PlainName />` in its own words, `withPlain(text)` for a string it shows, and the chat's Markdown does it in turri's words (never in code). What holds only text keeps `***plain`: a native menu, a tooltip, a placeholder, an aria-label.
- **Never "spec"** in what the person reads - the window, its menus, the docs, `APP_SURFACE`: it is ***plain ("no ***plain yet", the ***plain menu, show in the ***plain), or ***plain's own words for its parts - its description, definitions, intent. A functional spec keeps its name, as ***plain calls it. Code keeps its names (`SpecView`, `view: "spec"`). In Markdown, write it `\*\*\*plain` outside code.
- **The interface's own words are lowercase** - turri's brand: buttons, labels, headings, tooltips, placeholders, notices, sentences and all, and no CSS that shows them in capitals. What it shows as it is keeps its case: the ***plain, code, file names and paths, turri's messages, acronyms (API), other products' names (Finder, Mac) and keys (⌘R).
- Prose in docs, comments and user-facing strings uses British spelling and a spaced hyphen ` - `, not an em dash.
- Commit messages follow Conventional Commits, as in turri: `feat(ui): ...`, `fix(editor): ...`, the description lowercase and saying what the app now does.
- When what the window offers or how it is set up changes, update `docs/window.md` or `docs/development.md` - and the README's tour, if it says it - in the same commit.
